# Quality-Critical Contract

This reference expands the non-negotiable quality floor while keeping the entrypoint compact. Load only the sections triggered by the normalized task.

## Fact and identity evidence

- Classify inputs as source product, product URL, competitor reference, platform, locale/audience, or style. Competitor media never becomes product identity evidence.
- Build source understanding before prompts. AI visual reading is primary; OCR is conditional for uncertainty, small text, dimensions/specifications, warnings, or explicit user request.
- Preserve a byte-identical analysis original for every reference. Re-encode only when upload bytes/dimensions/format require it; the prepared derivative never replaces full-fidelity evidence.
- Deep-read every supplied reference, record membership/role/unique contribution/conflicts, then give ordinary downstream tasks a compact source-ID evidence summary. Missing coverage or unresolved conflicts fail closed.
- Select references per generation role and provider capability. Default to the strongest one or two user-owned sources; competitor/unknown references never enter product-generation requests, and “attach everything” is forbidden.
- Identity locks cover silhouette, proportions, color, material, structure, openings, lining, handles/straps, components, hardware, stitching, texture, motifs, labels, and micro-details. Unreadable marks remain unreadable.
- Apparel locks length, hem, collar-to-hem, sleeves, neckline, and silhouette. Bags lock body class, opening, bottom/side curvature, panel proportions, lining, strap/handle route, motif grid/scale, and source-supported scale.

## Physical truth

- Record confirmed functions, actions, use contexts, installation steps, scale reference, dimensions, forbidden generated mechanisms, and unsupported claims.
- Provider generation must be a descendant of the physical lock and fact gate when triggered.
- Do not generate unsupported magnetic, adhesive, press-lock, waterproof, load-bearing, movable, compatible, or dimension claims/actions.

## Canonical surface material

- For nail art, wraps, decals, tattoos, printed/woven textiles, and identity-bearing motifs, remove source background/UI/copy/watermarks and lock palette, temperature, lightness hierarchy, gradient direction, texture, shape, and source mapping.
- Adapt only perspective, curvature, occlusion, bounded environment light, and target scale. Do not freely redraw the material.
- After generation, require target region/mask, orientation mapping, projection evidence, and per-material visual pass for palette, lightness, temperature, gradient, shape, texture, and contamination.

## Copy, localization, and exact text

- Buyer copy must trace to supported facts. Internal QA language and unsupported performance promises never appear on final imagery.
- Visible copy passes text layout proof before provider generation. Check hierarchy, line breaks, overflow, mobile legibility, safe zones, and complex-script fit.
- Russian, German, Arabic, and other non-zh/non-en work requires source traceability, reviewer note, semantic/back-translation check, locale evidence, and script/RTL consistency.
- Final raster review blocks source-language residue, non-target-language residue, script mismatch, unreadable text, or unsupported claims.
- Exact personalized names/dates/monograms default to provider-generated weak/no-text base plus local typography compositor, compositor contract, layout proof, and final raster review.

## Photography, scene, and layout

- Every role has a buyer question, image job, shot/composition, camera/lens/light/scene intent, copy intent, prompt layers, and QA criteria.
- Lifestyle/use roles require a real generated or photographic scene asset. Vector decoration, repeated patterns, white-card product pasteups, and deterministic fake scenes fail.
- Cards and infographics use transparent or card-safe product assets. Visible rectangular residue or source/card background mismatch returns only to source normalization and affected layout.
- Avoid repetitive templates and translucent-card repetition; preserve role diversity and platform-native information density.

## Platform, commerce context, and durable style memory

- Platform/category evidence constrains ratio, information density, copy tone, gallery rhythm, and forbidden elements. Ozon ordinary categories default to `3:4`; only Ozon Fresh or current category evidence may replace that ratio.
- When the user confirms a platform/category trait, write only that reusable trait to platform preference memory. Never store product identity, private business/customer/supplier data, unsupported claims, or one-off failure feedback there.
- A request to create/save a store-wide style first reads available store URL/page evidence, offers 2–3 directions, and writes only a run-local draft. Persist store style only after user confirmation, using the allowlisted positioning/audience/visual/copy/prompt/evidence fields.
- A later matching store name/URL loads the saved style as an overlay before visual direction/prompt/QA. It never overrides current user instructions, source identity, physical truth, platform rules, compliance, or fresh research.
- Requests for bestseller/conversion/click/dwell performance trigger the commerce design research planner. Its click hook, dwell mechanism, trust objections, buyer questions, and gallery narrative must feed the compact blueprint, copy, prompt layers, and QA—not a standalone report pile.

## Generation pacing and repair

- Single formal images do not require anchors. Multi-image sets use 1/2/3 risk-adaptive anchors, then no more than two concurrent remaining roles after recorded anchor approval.
- Provider retries require evidence delta and respect role/run budgets. Circuit-open runs stop automatic retries.
- Keep approved assets. Repair only failed roles, materials, regions, text overlays, or layouts. Do not restart a full set because progress, manifest, lineage, overview, canvas, or final closure is stale.

## Run isolation, lineage, and delivery

- Every task has a unique run directory and run-local final manifest. Overview, QA, tldraw, and final gate read only that manifest or exact run `final-images`.
- Manifest lineage identifies provider-native, derived approved asset, repaired final asset, local text overlay, personalized overlay, crop, or other transformation with source and gate evidence.
- Reconcile generation progress from current-run child progress or manifest before delivery. Four-or-more image sets require an anchor pass decision.
- Multi-image delivery includes independent final images plus `overview/SET-OVERVIEW-contact-sheet.png`; the overview never substitutes final images.
- Every formal final delivery starts tldraw or records a safe blocked reason, runs QA loop routing, ledger/lineage/integrity gates, and passes Final Delivery Gate.
- Final Delivery Gate is an aggregator, never a root-cause retry node. Delivery closure may not generate images.

## Safety and communication

- Do not auto-publish/upload listings or promise CTR, CVR, ROAS, ACOS, rank, or sales.
- Default final images contain no platform-pack labels, watermarks, AI/system marks, SellerPilot, or Codex. Exact watermarks require explicit text, placement, purpose, and image scope.
- Keep keys, raw provider/network errors, machine paths, and internal permission details in diagnostics only. User updates report state, preserved assets, and the smallest safe next step.
